# Contributing to LogSpecter

Thanks for helping. Bug reports, new detection rules, tests, and docs fixes are all welcome.
This guide covers the local setup, the checks CI runs, how to add a rule, and the PR flow.

中文简述：先 fork 仓库，在新分支上修改，本地跑通 `pytest`、`ruff check .`、`ruff format --check .`
和 `logspecter selftest` 后提交 PR。新增规则必须附带用 `make_secret()` 生成的正样本，**禁止提交任何真实凭据**。

## Ground rules

- **No real secrets, ever.** Not in code, tests, issues, PR descriptions, or screenshots — not even
  revoked ones. All samples in this repo are generated by `make_secret()` in
  `src/logspecter/samples.py` from a fixed seed.
- Security vulnerabilities go through a private advisory, not a public issue. See
  [SECURITY.md](SECURITY.md).
- Keep PRs focused: one bug, one rule, or one feature per PR.

## Development setup

Requires Python 3.10+ (CI tests 3.10 – 3.13 on Linux, macOS, and Windows).

```bash
# fork on GitHub first, then:
git clone https://github.com/<your-username>/logspecter.git
cd logspecter
git remote add upstream https://github.com/Jeffy123-zhu/logspecter.git

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"            # pytest, pytest-cov, ruff
```

## Running the checks

These are the same commands CI runs (`.github/workflows/ci.yml`):

```bash
ruff check .                       # lint
ruff format --check .              # formatting (run `ruff format .` to fix)
pytest                             # unit tests
logspecter selftest --verbose      # recall on positive samples + zero false positives on negatives
```

Useful extras:

```bash
pytest tests/test_rules.py -q                 # one test file
pytest -k prefilter                           # tests matching a name
pytest --cov=logspecter --cov-report=term     # coverage
logspecter benchmark --size 64MB -j 2         # quick throughput / memory check for perf changes
```

CI also runs the test suite without `orjson` installed (the structured layer falls back to the
standard-library `json`), so do not import `orjson` directly outside `structured.py`.

Code style: ruff with `line-length = 100`, target `py310`. Existing comments and docstrings are
mostly in Chinese; either Chinese or English is fine for new ones.

## Adding a detection rule

The full field reference is in [docs/rules.md](docs/rules.md). The short version:

1. **Pick the pack.** Built-in rules live in `src/logspecter/rules/*.yaml` (`aws`, `azure`, `gcp`,
   `database`, `generic`, `private_keys`, `vendors`). Third-party SaaS tokens go in `vendors.yaml`,
   under the matching section comment.

2. **Write the rule.** Prefer a vendor prefix so the prefilter has a literal to anchor on:

   ```yaml
     - id: example-api-token            # lowercase kebab-case, globally unique
       name: Example API Token
       severity: critical               # critical / high / medium / low / info
       confidence: high                 # high / medium / low
       pattern: '\b(exm_[A-Za-z0-9]{40})\b'
       capture: 1                       # group holding the secret itself
       entropy:
         enabled: false                 # fixed-prefix structural rule: skip entropy gate
       tags: [example, credential]
       references:
         - https://docs.example.com/api/tokens
   ```

   Patterns are compiled as **bytes**, so `\b` and `\w` are ASCII-only. If the format has no
   distinctive prefix, keep the entropy gate on and use `keywords` + `require_keyword: true`
   (see `twilio-api-key-sid` and `datadog-api-key` in `vendors.yaml`).

3. **Add a positive sample** to `_build_positive_samples()` in `src/logspecter/samples.py`, built
   with `make_secret()` so it is random, deterministic, and fake:

   ```text
   ("example-api-token", f"EXAMPLE_TOKEN=exm_{g(_ALNUM, 40, rng)}"),
   ```

   `tests/test_rules.py::TestBuiltinRuleset::test_every_rule_has_a_positive_sample` fails if a rule
   has no sample. If the format is prone to false positives, also add a look-alike string to
   `_build_negative_samples()`.

   Add new samples at the **end** of the returned tuple: every `make_secret()` call consumes the
   seeded RNG, so inserting in the middle changes all samples generated after it.

4. **Check it.**

   ```bash
   logspecter rules show example-api-token   # "预筛" line must not be <full-scan>
   logspecter selftest --verbose
   pytest
   ```

   `tests/test_prefilter.py` verifies the prefilter never rejects a line your regex would match.
   A rule that cannot get a literal anchor should set `enabled: false`.

5. **Update counts in docs.** The README and README.zh-CN.md mention the number of built-in rules
   and selftest samples (`64 built-in rules`, `64 positive + 25 negative samples`); update them if
   you add rules or samples.

## Branches, commits, and pull requests

1. Sync with upstream and branch off `main`:

   ```bash
   git fetch upstream
   git switch -c feat/digitalocean-token upstream/main
   ```

   Branch prefixes: `feat/`, `fix/`, `docs/`, `test/`, `refactor/`, `chore/`.

2. Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

   ```
   feat(rules): add DigitalOcean personal access token rule
   fix(cli): exit with code 2 when --chunk-size is zero
   docs: add English version of the rule writing guide
   test: cover sysinfo.format_bytes
   ```

3. Push to your fork and open a PR against `main`. The PR template has a checklist; reference
   the issue with `Closes #<number>`.

4. CI must be green. A maintainer will review; please respond to comments by pushing new commits
   rather than force-pushing, so the review history stays readable.

## Finding something to work on

- Issues labelled [`good first issue`](https://github.com/Jeffy123-zhu/logspecter/labels/good%20first%20issue)
  are small and self-contained, with the files to touch and acceptance criteria listed.
- [`help wanted`](https://github.com/Jeffy123-zhu/logspecter/labels/help%20wanted) issues are
  larger or need some design discussion first.
- [`rules`](https://github.com/Jeffy123-zhu/logspecter/labels/rules) issues are new detection rules —
  a good way to learn the codebase.

Comment on an issue before starting so two people do not work on the same thing. If you want to
work on something without an issue, open one first (bug, feature, or new-rule template) so the
approach can be agreed before you write code.
